Pizzeria AI Code Walkthrough

Detailed explanation of how the AI is integrated

This document is meant to be read like a code walkthrough. It explains the imports, the service functions, the route, the frontend components, the API calls, the cart integration, and the reason broad prompts only looked weak when the primary model was quota-limited.

1. What is AI in this app?

The AI is not in Angular. Angular only collects the user prompt and sends it to the backend. The backend is where the AI lives. It first tries Gemini, then a second Gemini model, and only then a local parser. That is why the app can still function if the model API fails, but broad prompts can look less intelligent in that degraded mode.

Important correction: a request like “I want something spicy” should be handled by Gemini when the model is available. If you see a literal response, that usually means the model was rate-limited and the app had to rely on the local fallback path.
What was added recently: a second model-backed AI path that is more forgiving than the primary model and can interpret vague requests before the app falls back to the local parser.

2. End-to-end flow

User enters natural language in the assistant widget or Meal Builder page.
↓
Angular sends the raw text to POST /api/ai/order using AiOrderService.
↓
Backend loads real menu data from MongoDB (pizzas and ingredients collections).
↓
Primary Gemini model parses the request into intent + items + toppings + quantities.
↓
If primary Gemini fails, a secondary Gemini model is tried.
↓
If both model-backed paths fail, the local fallback parser runs.
↓
Backend validates every returned item against MongoDB and calculates the final price.
↓
Validated cart items are pushed into ShoppingCartService.
↓
The cart badge, cart page, totals, and order flow update from the real cart state.
↓

server.js import-by-import

  • require('dotenv').config() loads environment variables from .env.
  • express creates the HTTP app.
  • mongodb provides the MongoDB client and ObjectId.
  • cors allows the Angular dev server to call the backend.
  • body-parser parses JSON request bodies.
  • registerAiRoutes is the AI endpoint module.

server.js step-by-step behavior

  • It creates app and a Mongo client.
  • It sets the Mongo URL from MONGO_URL or defaults to localhost.
  • It mounts the AI route before the old pizza and order routes.
  • It exposes the existing APIs for pizzas, ingredients, users, orders, and admin stats.
  • It listens on PORT or port 7000.

routes/ai.js line-by-line explanation

Imports:

  • parseOrderWithGemini = primary model call.
  • parseOrderWithSecondaryGemini = backup model call.
  • parseFallback = local parser only if both models fail.
  • validateAndPrice = MongoDB validation + pricing.

Handler logic:

  1. Read req.body.text and reject empty or oversized input.
  2. Connect to MongoDB using the shared connection URL and db name.
  3. Read the authoritative menu collections into memory.
  4. Try the primary Gemini model.
  5. If the primary model fails, try the secondary Gemini model.
  6. If both fail, use the local fallback parser.
  7. Validate every item against MongoDB.
  8. Return a response with availability, totals, and cart-ready line items.

4. Detailed code walkthrough: Gemini service

geminiService.js

Imports / constants

  • GEMINI_MODEL = primary Gemini model name from process.env.GEMINI_MODEL.
  • SECONDARY_GEMINI_MODEL = backup Gemini model name from process.env.SECONDARY_GEMINI_MODEL.
  • GEMINI_TIMEOUT_MS = how long the app waits before aborting a model request.
  • QUOTA_COOLDOWN_MS = per-model cooldown after a 429 rate-limit response.
  • quotaCooldownUntilByModel = in-memory map tracking cooldown per model name.

Prompt blocks

  • SYSTEM_PROMPT_PRIMARY = strict parser prompt. It forces structured JSON and explains pizza/topping/custom rules.
  • SYSTEM_PROMPT_SECONDARY = more forgiving backup prompt for vague prompts like “something spicy” or incomplete wording.

Helper functions

  • buildMenuReference() turns the MongoDB menu arrays into a text block so Gemini can ground itself on real menu names.
  • getCooldownUntil() reads the model-specific cooldown timestamp.
  • markQuotaCooldown() starts the cooldown window when Gemini returns HTTP 429.
  • parseOrderWithGeminiModel() is the shared low-level caller used by both primary and secondary model paths.

Primary path

  • parseOrderWithGemini() calls the primary model with the strict prompt.
  • It returns structured JSON with intent and items.
  • It never decides availability or pricing.

Secondary path

  • parseOrderWithSecondaryGemini() calls the backup model.
  • This path exists so vague requests get a second AI attempt before the local parser runs.
Why this matters: This is the change that removes the “literal fallback only” behavior. The app is no longer dependent on just one model.
fallbackParser.js

Imports

  • extractLeadingQuantity() = parses “2 pepperoni pizzas” into quantity 2.
  • extractPeopleCount() = parses “for 10 people”.
  • servingQuantityForPeople() = converts group size into pizza quantity.

Main logic

  • stripLeadingFillers() removes filler words like please/can you/build me/add/make/order.
  • tryParseCustomization() recognizes “remove X and add only Y” or “only X and Y” and emits a custom pizza.
  • parse() handles group-size requests, custom topping-only requests, simple pizzas with toppings, and generic multi-item lists.
Important: This parser is still a safety net, not the primary intelligence layer. It is much better than before, but it is intentionally less capable than Gemini.
menuMatcher.js

Purpose

  • Maps AI-generated names to actual MongoDB pizzas and ingredients.
  • Tolerates simple spelling mistakes.
  • Provides recommendations for vague pizza requests like “a pizza”.

Functions

  • tokenize() normalizes text into comparable tokens.
  • levenshtein() calculates edit distance for typo tolerance.
  • tokensClose() decides whether two tokens are close enough to count as a match.
  • fuzzyOverlapScore() scores how well the query matches a candidate.
  • matchPizza() returns exact, fuzzy, or suggestion-based pizza matches.
  • matchIngredient() returns a matching topping or null.
  • extractLeadingQuantity() parses numeric and word-based quantities.
  • extractPeopleCount() finds “for N people/guests/adults/folks”.
  • servingQuantityForPeople() uses a 3-people-per-pizza heuristic.
orderValidation.js

Purpose

  • Validates each parsed item independently against MongoDB.
  • Builds the final cart items with real prices.
  • Allows a valid pizza to be added even if another requested topping/item is unavailable.

Important helpers

  • addStandaloneIngredient() adds a topping/side/drink that is meant to stand alone.
  • rawItem.type === 'topping' means the AI identified a standalone item.
  • rawItem.type === 'custom' means a pizza built only from toppings.
  • rawItem.type === 'pizza' means a fixed menu pizza item.

Validation behavior

  • Every pizza and every topping is checked separately against MongoDB.
  • Unavailable toppings do not block the available pizza.
  • Prices come from MongoDB only; Gemini pricing is ignored.
  • Response includes availableItems, unavailableItems, cartItems, total, and message.

5. Detailed code walkthrough: frontend

ai-order.service.ts

Imports

  • Injectable makes the service injectable application-wide.
  • HttpClient sends HTTP requests to the backend.
  • Observable is the async type returned by the HTTP call.
  • environment.apiUrl points to the backend base URL.
  • CartItem defines the cart payload shape returned from the backend.

What parseOrder() does

  • Posts raw user text to POST /api/ai/order.
  • Returns an observable of AiOrderResponse.
  • It does not interpret the text itself.
ai-order-base.ts

Purpose

  • This is the shared controller logic for AI UIs.
  • Both the floating widget and the Meal Builder page reuse it.

Fields

  • userText = current text input.
  • isLoading = UI loading state.
  • response = the last backend response.
  • errorMessage = human-readable UI error.

Methods

  • submit() sends the text to the AI service and pushes returned cart items into the real cart service.
  • goToCart() routes to /shoppingcart.
  • toppingNames() formats topping names for display.
  • startOver() clears the input and response state.
ai-widget.component.ts / html / css

What this component is

  • A global floating chat assistant mounted in app.component.html.
  • It is not a routed page and not a navbar tab.
  • It has chat history, assistant messages, loading animation, and voice input.

Imports and dependencies

  • Router is used so the widget can send the user to the cart.
  • AiOrderService sends the raw natural-language prompt to the backend.
  • ShoppingCartService adds validated cart items into the actual cart state.
  • AiOrderBaseComponent provides the shared submit logic.

Voice input

  • SpeechRecognition / webkitSpeechRecognition are detected dynamically on the browser.
  • If available, the microphone button appears.
  • The transcript is appended into userText.

Template behavior

  • Open/close floating panel with a robot button.
  • Show empty-state guidance when no chat exists.
  • Render each user and assistant message from the conversation array.
  • Show a Go to Cart button only when the backend actually added items.

CSS behavior

  • Fixed-position bottom-right launcher.
  • Pulsing ring animation on the button.
  • Slide-in panel animation.
  • Typing dots animation while the AI request is loading.
meal-builder.component.ts / html / css

Purpose

  • A dedicated full-page AI meal builder.
  • Uses the same service and same cart update logic as the widget.

Why it still exists

  • Some users prefer a full-screen guided experience over a floating widget.
  • Both UI surfaces use the same backend AI pipeline.
shopping-cart.service.ts

Imports

  • BehaviorSubject stores the live cart state.
  • Observable exposes the cart to subscribers.

Key methods

  • addToCart() adds a cart line if the id does not already exist.
  • addOrIncrementCart() is used by the AI pipeline to merge validated items into the cart.
  • removeFromCart() removes a cart item.
  • updateQuantity() changes item quantity and removes it if quantity drops to zero.
  • clearCart() empties the cart.
  • updateMessage() pushes the new cart state to subscribers and saves it to localStorage.
  • loadCart() restores persisted cart state on startup.
app.module.ts and app-routing.module.ts

app.module.ts

  • Declares the app root, menu pages, order pages, profile pages, and the floating widget.
  • Imports BrowserModule, FormsModule, HttpClientModule, and the routing module.
  • This is where Angular knows the widget exists.

app-routing.module.ts

  • Routes are defined for the regular pages and the Meal Builder page.
  • The old AI Assistant tab route was removed; the assistant now lives globally as a widget.
  • This is why the widget appears on every page instead of only one route.
app.component.html
  • Renders the navbar.
  • Renders the page router outlet.
  • Renders <app-ai-widget> once at the root so it is globally available.
  • Renders the footer.

7. How the API key is integrated

Where the key lives

  • The Gemini API key is only read in backend code.
  • It is loaded through dotenv from backend/.env.
  • The frontend only knows apiUrl and never sees the key.

What the backend does with it

  • process.env.GEMINI_API_KEY is read inside geminiService.js.
  • The key is placed on the Gemini REST URL as a query parameter.
  • The backend sends the request, not Angular.
Security rule: the key must never be copied into Angular environment.ts, HTML, or browser JavaScript.

8. Why some prompts still fail

When Gemini is available

The AI should understand broad prompts like “I want something spicy” or “build a meal for 10 people” because the second Gemini path can reason over the real menu names and return a structured recommendation.

When Gemini is rate-limited

The backend will degrade to the local parser. That parser is now smarter than before, but it is still rule-based. That is the difference between “AI reasoning” and “safe fallback parsing.”

The app is now AI-first with a secondary AI fallback, but if both model-backed paths fail, it is still possible to get a literal-looking fallback answer. That is expected and safe, not a broken cart flow.

10. One-line conclusion

The user text is sent to Gemini first, then validated against MongoDB, then pushed into the real cart state. The fallback is now a second-step safety net, not the primary experience.
