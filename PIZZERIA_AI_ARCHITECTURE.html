Pizzeria AI Integration Guide

How the AI is actually wired in this app

This document explains the real frontend-to-backend flow, what Gemini does, what the fallback parser does, where MongoDB is used, how cart updates happen, and why a broad prompt sometimes looks like a rule-based reply.

1. The real AI flow

The app does not parse the user request in Angular first. Angular sends the raw natural-language text to the backend. The backend first tries Gemini. Only if Gemini fails, times out, returns invalid JSON, or is rate-limited does the app fall back to a local parser.

User types: “I want to eat something spicy” or “build a meal for 10 people”
↓
Angular AI widget / Meal Builder page sends the raw text to POST /api/ai/order
↓
Backend calls Gemini with a system prompt, the raw user message, and a list of real menu names
↓
Gemini returns structured JSON: intent + items + toppings + quantities
↓
Backend validates each item against MongoDB and computes authoritative prices
↓
Validated cart items are pushed into the existing ShoppingCartService
↓
Cart badge, shopping cart page, and totals update from the real cart state
↓
Angular shows the assistant response, availability, total, and a Go to Cart button only when items were actually added
↓
Important: The fallback parser is not the same thing as Gemini. If Gemini is rate-limited, the backend still works, but the fallback is intentionally conservative and may not reason like a large language model. That is why a request can look less intelligent when the quota is exhausted.

2. Why conditions exist

The conditions in the backend are not replacing the AI. They are safety gates after the AI step.

  • They validate that returned item names exist in MongoDB.
  • They reject invented pizzas, toppings, or prices.
  • They keep valid items when an invalid item is also present.
  • They make the cart state authoritative, not the model output.
Good example: Gemini says “Chicken Tikka + Mushrooms + Coke”.
Backend adds Chicken Tikka and Mushrooms, but marks Coke unavailable.

3. Why “eat something spicy” can look wrong

If Gemini is available, it can infer broad intent like “I want something spicy” and turn that into structured output. If Gemini is not available, the fallback parser may not have enough semantic intelligence to guess the right menu item.

During your testing, Gemini was rate-limited, so the app was falling back more often than usual.

In other words: the app architecture is AI-first, but in a quota failure it degrades to a safe parser, not a second AI model.

Global widget behavior

  • The assistant opens as a floating orange chat bubble in the bottom-right corner.
  • It stays available on every page because it is mounted in app.component.html.
  • It includes optional voice input using the browser's Web Speech API.
  • It keeps conversation history inside the widget so you can see the back-and-forth.

Meal Builder page behavior

  • The page uses the same AiOrderService call as the widget.
  • It is better for a full-screen, guided meal-construction flow.
  • It still ends in the same shopping cart update path.

5. Backend architecture

File What it does Why it matters
backend/server.js Express app bootstrap. Registers the AI route and the existing CRUD routes. Owns the HTTP surface of the app.
backend/routes/ai.js Implements POST /api/ai/order. Orchestrates Gemini, fallback parsing, MongoDB validation, and response formatting.
backend/services/geminiService.js Calls Gemini with the system prompt, schema, timeout, and quota cooldown. Primary natural-language understanding step.
backend/services/fallbackParser.js Deterministic parser used only when Gemini fails or is rate-limited. Safety net, not the primary AI.
backend/services/menuMatcher.js Matches user language to real pizza/topping names, including typo tolerance. Stops invented products and improves matching for fuzzy text.
backend/services/orderValidation.js Validates every returned item against MongoDB and calculates authoritative totals. Source of truth for menu existence and pricing.

What MongoDB stores

  • pizzas collection: name, price, description, image, type, rating.
  • ingredients collection: topping/ingredient name, price, image.
  • users collection: login and profile data.
  • orders collection: saved completed orders.

Why MongoDB validation is mandatory

  • Gemini can understand language, but it is not the source of truth for the menu.
  • The backend must stop invented items from entering the cart.
  • Prices must come from MongoDB, not the model.

7. What the AI response means

The backend returns a structured response that the frontend can render directly. The important fields are: 

{
  "success": true,
  "usedFallback": false,
  "intent": "ADD_TO_CART",
  "availableItems": [],
  "unavailableItems": [],
  "cartItems": [],
  "total": 0,
  "anyAdded": false,
  "message": ""
}

availableItems

Validated items that can be added to the cart, with toppings and quantities preserved.

unavailableItems

Requested items that were not found in MongoDB or could not be used.

cartItems

The exact line items the frontend pushes into the existing cart service.

anyAdded

Controls whether the UI shows Go to Cart and whether the cart state changed.

8. Why the assistant previously looked inaccurate

Cause 1: Gemini quota exhaustion
When the API returned HTTP 429, the backend fell back to the local parser. That parser is safe, but it is not a full LLM.
Cause 2: Conservative fallback
The fallback parser used to understand only a few exact phrases. Broad prompts like “eat something spicy” could end up as an unmatchable literal request.
What was improved
We added broader filler-word stripping, fuzzy matching, custom-pizza handling, and people-count reasoning so the fallback behaves much closer to a human-facing assistant.

9. Dependency map

Backend direct dependencies

  • express – HTTP server.
  • mongodb – database client and collections.
  • cors – cross-origin access.
  • body-parser – JSON body parsing.
  • dotenv – loads .env for the Gemini key and Mongo URL.
  • mongoose / nodemon – present in package but not central to the AI flow.

Frontend direct dependencies

  • @angular/core, @angular/router, @angular/forms, @angular/common/http.
  • rxjs for async cart and HTTP observables.
  • bootstrap and Font Awesome for styling and icons.
  • The browser’s built-in Web Speech API for voice input when available.

10. End-to-end examples

Prompt What Gemini / fallback should infer What backend does

11. The short version

Yes, AI is used. The user message is sent to Gemini first. The frontend does not decide the menu item. The backend only validates the result against MongoDB and computes prices. If Gemini is unavailable, the app uses a conservative fallback parser so it still works, but that fallback is not equivalent to an LLM.

If you want the fallback to behave more like a true conversational model when Gemini is rate-limited, the next step would be to either improve the fallback with more semantic rules or replace it with a second model-backed provider. The current app, however, is already wired correctly as AI-first with backend validation.
